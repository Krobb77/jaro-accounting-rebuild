## Phase 0 — Foundation (2026-10-06)

### Cross-cutting

- **SQLite for local verification, Postgres as deploy target.** Postgres is not installed in this environment. Migrations target Postgres DDL but are kept SQLite-runnable; Postgres-only features (advisory locks) sit behind an interface with a threading fallback. DB roles (`jaro_web`, `jaro_worker`, `jaro_migrate`) are string-checked locally, enforced at deploy. (Build team)
- **Table count is 30, not 31.** The plan's "31" is an arithmetic slip: 26 baseline + 4 added (invitation_events, password_resets, terms_versions, terms_acceptances) = 30; login_events folds into audit_log per D-16. No table is missing. (Build team, corrected detail)
- **Session cookie `Path=/`, not `/portal`.** The plan's DONE criterion (Path=/portal + `__Host-` prefix) is self-contradictory: RFC 6265bis requires `__Host-` cookies to carry `Path=/`. Chose `Path=/` as the correct behavior. Flags are otherwise exactly `HttpOnly; Secure; SameSite=Lax` + `__Host-`. (Build team, corrected detail)
- **Sync SQLAlchemy** (not async) for the backend — simpler worker/lease-claim code, no performance need at this scale. The venv ships no async DB driver; sync runs unchanged against Postgres with psycopg2. (Build team)
- **UUID PKs as `String(36)`** holding uuid7 values (portable across Postgres/SQLite; no pg extension needed). Lexicographic order == chronological for uuid7. (Build team)
- **citext → `lower()` functional index; Postgres `text[]` → JSON** in migrations for SQLite compatibility. (Build team)
- **Advisory locks abstracted** (`app/advisory.py`): `pg_advisory_xact_lock` on Postgres; a process-local threading-lock registry on SQLite. The SQLite fallback is NOT cross-process — local verification only. (Build team)
- **Migrations import type aliases from `app.models`** (CIText, StrList, UTCDateTime) but define every Table inline — frozen DDL per migration, shared stable primitives only. (Build team)
- **Calendar provider stubbed** — provider-agnostic `calendar_blocks` interface; Google API vs CalDAV wiring awaits Jared (owner question #1). (Build team)
- **Mail templates are Phase-0 placeholders** — real HTML templates land with their features (invitation email exists as reference asset; production rendering wired in Phase 5). (Build team)
- **Rate budgets are starting values** — tuned in Phase 4 per D-21. (Build team)
- **Terms v1 body is an honest placeholder** marked "draft": registry, hashing, and acceptance machinery ship in Phase 0; final copy authored with Jared in Phase 5. (Build team)
- **Absolute session cap is 12h** (D-02), overriding ARCH §2.1's 24h note. (Build team)
- **`MAIL_ALLOW_SEND` unset refuses boot** — the gate is explicit rather than defaulting, so a missing var can never silently enable sending. (Build team)
- **No `app` object at import time.** `uvicorn app.main:create_app --factory` is the entry point; importing the module never boots (H2). (Build team)
- **Rate-limit increments run in their own short-lived transaction**, not the route's: a route rollback must not refund the attempt (otherwise floods get free retries). (Build team)
- **`verify_runtime` derives the pinned head from the migration scripts on disk** (code is the pin, not configuration) and enforces a single head. (Build team)
- **`frozen_snapshot.fields.destination` carries the raw address.** ARCH stores `destination_hash` (A6) on the row; the worker still needs the address to render. The snapshot is the render-truth (E2); the hash is the PII-safe reference for logs/eligibility. (Build team)
- **Crash-recovery reclaims `sending` rows with expired leases.** The first cut of the claim query only matched `queued/retry`, which would strand crashed workers' intents forever. Fixed and covered by the kill-mid-send test. (Build team)
- **SMTP backend exists but is never exercised in tests** (`MAIL_ALLOW_SEND=false` everywhere in tests). The gate is enforced in `SmtpMailBackend.send` AND at settings validation (defense in depth). (Build team)

## Phase 4 — Verification, ops hardening, cutover (2026-10-06)

- **A4 transaction race — REAL BUG FOUND AND FIXED:** final verification caught an intermittent `401 session_expired` in the portal Playwright journeys (3 different tests failed across runs; each passed in isolation). Root cause: FastAPI sends the response BEFORE closing the request `AsyncExitStack`, so the `get_db` yield-teardown `db.commit()` landed after the client could fire its follow-up — the follow-up's SQLite read snapshot predated the commit (`ROW NOT FOUND` for a valid session). Fix (generalizable pattern): new `backend/app/transactions.py` `TransactionMiddleware` commits the route's session AFTER `call_next` returns the response object but BEFORE bytes are sent; `get_db` now only stashes the session on `request.state.db_session` and closes it. All five test `get_db` overrides updated to the same contract (and their `Request` imports moved to module level — FastAPI resolves override annotations against module globals, not closure locals; a closure-local import silently mis-resolves `request` as a required query param → 422). New regression test `test_17_18_session_committed_before_response_sent`. Verified: 0/160 immediate read-after-write failures post-fix (was ~8/240 pre-fix); portal journeys 6/6 ×3 runs.
- **Worker `-m` CLI entry point** (`app/worker_main.py`) — the Phase-0 residual: `Worker` + `run_once()` were complete and tested; the CLI wrapper was deferred. Thin wiring only (settings → `verify_runtime` → engine → session factory → mail backend → `Worker.main()`); `--once` for smoke/cron; refuses non-`worker` workload (G2) and fails closed on bad config (H2). (Build team)
- **Rate budgets remain starting values** (D-21) — load-test and tune with Jared before launch; the numeric allowances are owner question #12. (Build team)
- **Backup drill undrilled** — runbook states it honestly (H6); tracked open item with owner (Jared) + target date (onboarding week). (Build team)
- **No live email ever sent** — every test and drill ran in capture mode; production sending needs the explicit `MAIL_ALLOW_SEND=true` + `MAIL_BACKEND=smtp` opt-in plus SPF/DKIM/DMARC (cutover §4). (Build team)

## Fixes from preview + flake investigation (2026-10-13)
- **TOTP enrollment boundary tolerance (amends D-36).** Root cause of the flaky Playwright portal-journey test: `verify_enrollment_pair` required (current,next) codes exactly, so a client reading two codes just before a 30s rollover failed when the server verified just after — ~10% flake per enrollment, and the same failure would hit real users. Fix: accept (prev,current) or (current,next); the D-36 security property is unchanged (caller still proves two consecutive valid codes). Lives in: `backend/app/totp.py`. New tests: `backend/tests/test_19_totp.py` (4 tests, incl. a pinned rollover-boundary case that fails on the old code).
- **h1 missing bottom margin.** The CSS reset zeroes all margins; base gave h2/h3 `margin-block-end` but h1 was missed, so the login page's "Client sign in" heading collided with the posture line beneath it. Fix: `h1, h2, h3 { margin-block-end: var(--space-5); }` in `frontend/src/css/base.css`. The hero h1 is unaffected (sets its own margin explicitly). Verified via screenshot.
- **Rate-limiter `source` dimension was shared across budgets (real product bug, fixed 2026-10-13).** The `source` dimension key omitted the budget name, so every rate-limited request from one IP incremented a single global counter — browsing availability/slots burned through the booking.confirm per-IP allowance and produced spurious 429s (caught via the Playwright booking journey: the manage-page reschedule POST 429'd after earlier tests ran). Fix: namespace the `source` dimension by budget (`f"{budget}:{source}"`); the dimension name keeps it distinct from `route_source`. In production this would have 429'd real users after ~30 total requests of any kind from one IP. New regression test: `test_source_dimension_is_per_budget` in `backend/tests/test_06_rate_budgets.py`.
- **Journey-test races fixed (test-only, no product change):** (a) the portal first-run tests read `#totp-manual-key` before the async `/2fa/enroll` POST populated it (modal is unhidden first, key set later) — empty key → wrong TOTP codes → 15s timeout; new `_read_manual_key()` helper waits for non-empty key (2 call sites).
